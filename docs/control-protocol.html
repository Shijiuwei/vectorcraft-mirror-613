Control protocol

Last updated: 2026-10-25 · Change: brush library panels (window.brushLibrary, window.brushLibrary.other, ui.saveBrushLibrary); previously: Transform Each opens on the values it was last confirmed with; its Copy button confirms with copy: true (#1732); previously: panel docking on craft-ui's layout: ui.docking, the parameters of window.panel.float and window.panel.dock; previously: ui.screenshot's 64 MiB inline-PNG cap and its path-plus-data downgrade; symbol library panels (window.symbolLibrary, window.symbolLibrary.other, ui.saveSymbolLibrary); synthetic input budgets (#1709); bounded transport waits (#1726).

vectorcraft --control <port> listens on 127.0.0.1:<port> (loopback only). The port must be a number from 1 to 65535 (--control=<port> works too), given once; otherwise the app prints an error and exits before it starts. One JSON request per line: {"id": 1, "method": "ui.inspect", "params": {}} → {"id": 1, "ok": true, "result": {...}} or {"id":1,"ok":false,"error":"..."}.

Set VECTORCRAFT_CONFIG_DIR to a dedicated directory for an isolated native test profile. Preferences, logs, recovery and user libraries then use that root, without importing the legacy DrawCraft profile. An unset override preserves the usual platform paths and legacy migration; an explicitly empty override disables those paths. VECTORCRAFT_NO_PREFS continues to disable preference reads and writes. Without the override, a portable.txt or VectorCraft.portable file beside the executable (as in the Windows portable zip) puts that root in VectorCraftData next to the executable; on macOS the marker and the folder sit next to VectorCraft.app, for an AppImage next to the .AppImage file, and a Flatpak install has neither. VECTORCRAFT_NO_PREFS never looks for the marker or creates the folder.

Only requests are read. Every line must be a JSON object with a string method (id and params are optional; blank lines are skipped). Anything else gets one error reply ({"ok": false, "error": "… closing the connection"}) and the server closes the connection, so nothing sent after it on that connection runs. That covers text that isn't JSON, a JSON array or number, an object without method, invalid UTF-8, and a line longer than 4 MiB. An HTTP request (for example a web page's cross-origin fetch to 127.0.0.1:<port>) therefore can't smuggle a command in its body: its request line is rejected first. At most 16 connections are served at once; further ones get an error line and are closed. Clients that get an error reply should reconnect. The port has no authentication, so only enable it while you use it. Idle clients have 5 minutes to start their next line; once the first byte arrives, the complete line must arrive within an absolute 30 seconds (trickled bytes do not renew it). A reply has 60 seconds to be written. Expiration closes the connection and returns its slot (an idle connection is closed without a line, so nothing waits where the next reply would be; a line that stalls gets the usual error line first); persistent clients can send further requests within these bounds, or reconnect after idle expiration. These transport budgets are separate from the existing 60-second command-processing wait. Transport: apps/vectorcraft/src/control_server.rs.

Synthetic input budgets

ui.drag accepts at most 256 steps; ui.click and ui.drag accept at most 16 count. They must be non-negative JSON integers. Omitted values keep their defaults (8 steps, one click); explicit zero still acts as one, as before. Oversized or malformed values return an error before any move, press or release is queued.

All synthetic methods (ui.key, ui.text, ui.move, ui.click, ui.drag, ui.wheel) share a 1,024-event pending-queue limit. The whole request must fit; rejection preserves existing input and does not append a partial gesture. Clients can retry once earlier input has drained. At most 64 control requests run per frame; later requests remain on the channel and another frame is scheduled. These limits cover synthetic input admission, separately from socket transport and command-processing timeouts.

A request the app hasn't answered after 60 s gets {"ok": false, "error": "timeout: …"}. If the app had not started it (it was busy, or its window wasn't being drawn), the request is withdrawn and never runs, and the error says "will not run": retrying is safe. If the app was already running it, the error says "still running": it may yet complete, so check the document before retrying. On macOS the app keeps itself out of App Nap while the control channel is on, so it keeps answering with its window hidden, minimized or covered, or with the screen locked.

Confining file access

vectorcraft --control 7979 --automation-read-root /work/project --automation-write-root /work/project/out

--automation-read-root <dir> and --automation-write-root <dir> (or VECTORCRAFT_AUTOMATION_READ_ROOT / VECTORCRAFT_AUTOMATION_WRITE_ROOT; --flag=<dir> works too) confine what the control channel reads and writes, with the same flags as vectorcraft-cli mcp and the other Craft apps. Every path a request reads (open, place, relink, library and profile loads, plug-ins…) must lie inside a read root, every path it writes (save, export, package, captures, library saves…) inside a write root; anything else is an ordinary error reply. Paths are made absolute against the app's working directory, links are followed (for a file that doesn't exist yet, its folder's), and the comparison is by whole folder names (/work2 is not inside /work), ignoring case on Windows; .. below a folder that doesn't exist, a link that leads nowhere and Windows device names are refused. A root left out grants none of its access. The roots must be existing folders, or the app doesn't start; without --control they are ignored. See docs/mcp.md › Confining file access for the details.

Each root flag may be given more than once, a path inside any of its folders being allowed (#3546); the command line's folders of a kind replace its environment default. Missing or empty values and another option used as a value stop the desktop before it starts any services, even without --control. For a folder name starting with -, use --flag=-folder or the relative path ./-folder.

What is confined: the requests themselves, the frames that carry input they inject (ui.click, ui.key, ui.text…, so a menu item an agent clicks is confined too), the background saves and exports they start, and window captures. The person at the keyboard is not: files opened from the command line, Finder or a file dialog, and everything done with the mouse and keyboard, work as usual. The preferences that move folders the app reads or writes on its own (Additional Fonts Folder, Additional Plug-ins Folder, Data Recovery's folder, the Templates folder) can only be pointed inside the roots by automation. The app's own folders (preferences, Data Recovery, the library folders, VectorCraft's Fonts folder) are not confined, since no agent names a path there. A path is checked, then opened: another program that swaps in a link between the two can still win that race.

Shared panel docking

The canvas and the panels form one craft-ui docking layout: the protected canvas panel beside a dock at the window's right edge. The dock's columns, from the window edge inwards, are the Properties | Layers | Libraries column, the icon column (one group per row of icon panels) and any columns the user adds. Floating windows hold groups stacked top to bottom or split side by side. Workspaces save the layout (ui.docking in ui.inspect; absent while the workspace was never customized and its layout follows ui.dock_tab, ui.dock_collapsed and ui.dock_width) and where each hidden panel was (ui.docking_hidden). ui.inspect has no floating_panels.

Parameters from VectorCraft's own docking, on window.panel.float and window.panel.dock:

  • onto: as a tab of the group holding that panel. On float that group must float; on dock it is anchor.
  • above, below: as a group of its own above or below the group holding that panel, in its floating window or dock column.

ui.docking (a control method, read only) returns:

  • layout: the layout in use; customized: whether the workspace has a saved layout; hidden: the hidden panels with a remembered place.
  • flyout: the panel open as a flyout from an icon column; focused: the panel the user last clicked or pressed in; autoCollapse: flyouts close on a press outside them; panelsShown: false while Tab or a full screen mode hides the panels.

Groups, columns and windows are named by their first panel.

Floating windows in OS windows of their own (the desktop): hitRects leaves out their controls, and ui.pointer, ui.click and ui.drag reach the main window only, so drive them with commands. Such a window's place on screen is floating[].native in the layout (rect is where it would float inside the app window). Keys typed in one run the main window's shortcuts; modal dialogs block them.

Synthetic input hardening checklist

  • Validate counts and reserve the whole gesture before queue mutation.
  • Bound pending events across all synthetic methods, preserving rejected requests' prior queue.
  • Yield after a finite control-request batch per frame; retain later requests and schedule another frame.

Transport hardening checklist

  • Bound idle, partial-line and reply-write waits without renewing a partial-line deadline per byte.
  • Release connection slots on worker exit, including timeout and failed worker creation.
  • Preserve correlated replies and persistent connections within the transport budgets.
