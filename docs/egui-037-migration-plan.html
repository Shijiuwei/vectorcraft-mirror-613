1. Executive decision

Migrate VectorCraft from its pre-migration coherent egui 0.36.2 family (then resolved from crates.io, with craft-ui and craft-window pinned to 0.36-era craft-libs revisions) to the selected egui 0.37.0 family and the suite's winit 0.30.13 language fork, in a sequence that never leaves main with a mixed or unbuildable dependency graph.

The migration is not a version-string bump:

  1. The app already has the eframe::App::logic / App::ui split and a root Ui on 0.36.2. That split is not a 0.37 feature and must not be rewritten wholesale. The real work is to make the split honest: background tick work must not read stale UI input or stale i.time while the window is hidden, input must be consumed only in a known UI phase, and the UI pass must not duplicate side effects when egui runs a second layout pass. raw_input_hook is called by both native and web hosts before they decide whether to run a full update or logic-only; it marks a host iteration, not a UI phase.
  2. 0.37's WidgetType → accesskit::Role deprecation/alias and variant renames, Id/IdSalt split, Ui::scope_id, screenshot callback, FontsView privacy, ScrollArea::State::offset privacy, WidgetInfo.role, MouseWheelSource and accesskit::Role changes are concrete compile/API changes. The historical diagnostics in /home/codex/work/ssd2/task-evidence/egui037-audit-20261022/{fork,stock}/vectorcraft.errors already list many of them (35 entries; the fork and stock lists are identical). They are line-drifted clues, not a current acceptance baseline.
  3. The app has three behaviours that need explicit redesign, not mechanical renames:
    • screenshot completion (ui.screenshot reads a removed Event::Screenshot and egui::UserData); the final design is a bounded per-request completion slot whose callback holds only a weak slot reference;
    • native/web clipboard input (0.37 makes eframe's clipboard feature opt-in, and adds PasteImage / MiddleClickPaste), including the winit-owned W15P PRIMARY path routed through E4;
    • IME replacement and outgoing surrounding text (ImeEvent::DeleteSurrounding upstream; DeleteSurroundingBytes in the selected fork; E21b IMEOutput payload for W27) for the canvas's custom text tool.
  4. Accessibility is now a build gate: egui_kittest 0.37 fails an input widget with no accessible name, and the kittest harness sets MissingGlyphPolicy::Panic; production layout uses the default Tofu policy. VectorCraft has many custom painted fields and custom combo boxes; every visible input needs a real name and role, not just a painted label.
  5. egui 0.37 no longer enables default_fonts by default. VectorCraft's theme::install_fonts starts from FontDefinitions::default(); without the explicit feature its default families are empty, so text silently lays out as synthetic tofu in production and the install_fonts non-empty-family assertion fails. Enable egui/default_fonts explicitly: kittest's own [dev-dependencies] fonts do not reach VectorCraft's tests.

Selected dependency set (primary): approved, reachable storytold/winit revision containing W1–W15 (minus W5, plus replacement W20) and W17–W27 plus W15P and the bounded transfer API (D1a), and the complete storytold/egui P8 revision containing P2b, P7, P7b/E21b and P7c (D1b). Final SHAs are execution prerequisites created by that fork work; none is invented or asserted in this plan, and no intermediate fork stage becomes a production pin. The aiongg craft/0.37 (a4f9a17…) and winit craft/0.30.13-lang (8b35388b…) trees remain research inputs, not production pins. Fallback: none for production. Stock 0.37.0 is the measurement/attribution arm only; it lacks E21b, W15P and P7c, so it cannot substitute for D1b. If the fork work cannot land, stop and report the open gates rather than publishing a mixed or reduced graph.

2.4 Historical 0.36.2 lifecycle (planning snapshot, not current acceptance)

The 0.36.2 baseline already had:

  • App::logic(&mut self, ctx, frame) and App::ui(&mut self, ui, frame) in both hosts.
  • VectorcraftApp::logic(ctx) called from the host logic, guarded by vectorcraft_engine::guard::catch_panic.
  • VectorcraftApp::ui(ui) called from the host UI, also guarded.
  • A root Ui in App::ui; panels are already shown with egui::Panel::…::show(ui, …).
  • Custom Area/Window dialogs and floating panels in the 0.36.2 baseline; at planning time the app had no show_viewport_deferred/child native viewports. The shared-docking integration now opens desktop floating panels as craft-ui OS windows, while the web and Wayland keep them in-page (see “Shared-docking integration (current)” above).
  • ctx.run_ui in many tests; ctx.run_ui in test helpers draws either the whole app or one panel/dialog.

What 0.37 makes explicit:

  • eframe calls App::logic inside egui_ctx.run_ui, then App::ui, so both are called once per layout pass, not once per outer frame. A Grid created for the first time calls Context::request_discard, so the same outer frame can run App::logic and App::ui more than once. The host calls App::raw_input_hook once before that closure, not once per pass.
  • When a window is hidden/minimized/occluded, native eframe runs Context::run_logic instead of run_ui, and web runs run_logic after seeing that the tab is hidden. That leaves the last pass's InputState (events and time) in place; only viewport state is updated. Reading ctx.input events or i.time in logic-only iterations replays or mis-times work. Stale events must therefore be consumed only in a known UI phase.
  • raw_input_hook is not a UI-phase marker. Native EpiIntegration::update_logic_only calls prepare_raw_input(), which calls app.raw_input_hook(); web AppRunner::logic calls self.app.raw_input_hook() before it decides visibility and calls run_ui or run_logic. Both hosts call the hook for full and logic-only iterations. It is useful as a host-iteration boundary, not as evidence that a UI pass will follow.
  • Context::run_ui passes the existing root Ui; Context::root_ui panics if called while that Ui is borrowed. VectorCraft must not call root_ui from inside its App::ui or tests.
  • ViewportCommand::RequestPaintWhileHidden exists for a hidden window that must draw once (a dialog, a control request, a screenshot). A pending Screenshot command already asks for paint while hidden. A forced hidden UI pass is still a UI phase and must consume the input it was forced to present.
  • Context::cumulative_frame_nr() advances once when a run_ui completes (not per pass and not in run_logic); Context::cumulative_pass_nr() advances per layout pass, including a discarded rerun. Keep these distinct from the app's host-iteration counter in §4.2.

3.5 Screenshot path

Current:

  • crates/ui-egui/src/lib.rs::drain_control turns control::Outcome::Screenshot into a queued token and a PendingScreenshot with path/data/reply/deadline.
  • issue_screenshots sends ViewportCommand::Screenshot(UserData::new(token)).
  • collect_screenshots scans ctx.input(|i| i.raw.events) for Event::Screenshot { user_data, image, .. }, maps the token, and writes the PNG through control::save_screenshot.
  • PendingScreenshot times out after settle + 8 s with a user-facing "no frame presented" error.

0.37:

  • ViewportCommand::Screenshot(ScreenshotCallback); Context::request_screenshot is the convenience API.
  • ScreenshotCallback stores a one-shot FnOnce(Arc<ColorImage>) + Send + 'static; clones share it; completion is at most once; it does not request a repaint.
  • Event::Screenshot and UserData are gone.
  • A pending screenshot asks the integration to paint even while hidden (the command's documentation says so).

Required design (shared weak completion slot, per the suite capture contract):

  • PendingScreenshot owns Arc<CompletionSlot>, where the slot holds the optional Arc<ColorImage>, a strong Context/owning-viewport wake handle for the owning-viewport wakeup, and a live/canceled state. The request record owns the strong slot; the app keeps request id, path, data flag, reply sender, settle policy and deadline. Correlation comes from ownership of that slot, not a second token map or callback order.
  • issue_screenshots creates ScreenshotCallback::new with a closure that captures only a Weak<CompletionSlot> and the callback receives pixels only. The closure stores the image in the live slot, releases the slot lock, then wakes the owning viewport through the strong Context/owning-viewport wake handle the live slot owns; the detached callback never strongly captures Context. That slot-owned wake is the only scheduling: the callback itself has no implicit wake and requests no repaint. No PNG encoding, file write, command, Services access or long lock on the callback thread. A callback that fires after timeout/close finds the slot canceled and drops the image.
  • Keep collect_screenshots on the UI thread: take the image once, verify the request is still live and its geometry epoch is unchanged, then write through control::save_screenshot under file_access::confine. A late or stale result writes nothing and sends no second reply.
  • Serialize at most one outstanding capture at a time (the current code can issue several due commands in one frame; a one-shot callback makes correlation easy, but serializing avoids integration differences and bounds readback memory). Keep the settle-frame policy and the ~8 s deadline.
  • Admission is a pre-issue reservation, not just a post-hoc cap. Use the shared defaults: 4 pending requests, 128 MiB per image and 256 MiB aggregate reserved in-flight/completed bytes, calculated with checked width × height × 4 arithmetic, never evicting an earlier request. A stricter explicit budget is allowed only when a documented intended surface fits it (CADCraft's smaller budget is the example); 4/128/256 MiB admits a 3840×2160 logical viewport at 2× (≈126.6 MiB) and must not be raised. Reject excess admission with a control error before issuing, release the reservation on drain/timeout/cancel, and account for renderer/readback transient allocation separately in peak RSS.
  • Bind a geometry epoch at issuance. Record the target UI's known logical content and screen bounds, viewport id, pixels_per_point and a surface/geometry epoch. Before saving, reject or retry on any resize, DPI, zoom or surface-epoch change since issuance, including a change back to the original values. Do not assume Wayland inner_rect exists or that callback arrival supplies capture metadata; with an unchanged epoch derive the pixel scale from the returned image dimensions and verify aspect and rounding.
  • Hidden issuance needs a paint request. The Screenshot command itself forces a paint while hidden, but a request queued in app logic and not yet issued — including every remaining settling frame — must send ViewportCommand::RequestPaintWhileHidden from logic so a UI pass reaches issuance. A bare request_repaint() only runs hidden logic, and callback arrival does not wake by itself.
  • This app is one of the eleven existing craft-ui consumers, so it adopts the already-issued shared craft-ui completion-slot helper from L2 (CL-1 + CL-2F). VectorCraft keeps no app-local or provisional capture slot: the API must be frozen before the atomic compatibility PR lands.
  • Keep the existing response schema: {ok, result: {path?, width, height, pngBase64?}} and the explanatory timeout error. The inline pngBase64 copy is capped at 64 MiB; when the request named a path, write that file and omit only the oversized inline copy (a path-less data: true request fails before encoding). docs/control-protocol.md documents this downgrade. It says a minimized/covered window fails after ~8 s; 0.37 may now paint a hidden window, so re-test and update the doc only with evidence.

4.2 Lifecycle: host iteration, input and UI

Split the current logic into an explicit, testable boundary. Proposed surface in crates/ui-egui/src/lib.rs:

VectorcraftApp::begin_host_iteration()  // called from both hosts' raw_input_hook; root viewport only
VectorcraftApp::tick(ctx)               // once per host iteration, full or logic-only; no raw input
VectorcraftApp::ui(ui)                  // first UI pass in an iteration consumes input; later passes draw only

Hosts:

  • apps/vectorcraft/src/main.rs::App::raw_input_hook calls self.app.begin_host_iteration() before injecting host input and synthetic events; App::logic calls self.app.tick(ctx).
  • apps/vectorcraft/src/main.rs::App::ui calls self.app.ui(ui).
  • apps/vectorcraft-web/src/web.rs::WebShell::raw_input_hook calls app.begin_host_iteration() before taking its pointer events; WebShell::logic calls app.tick(ctx) and keeps graphics-loss/restart and api::poll_replies.
  • WebShell::ui keeps its DOM paste/drop handling and calls app.ui.
  • This matches the actual host order: eframe calls raw_input_hook from prepare_raw_input in both EpiIntegration::update and EpiIntegration::update_logic_only; web AppRunner::logic calls it before checking visibility and before run_ui/run_logic. It is a host-iteration boundary, not a UI-phase marker. It is also called for a child-viewport update; VectorCraft has only the root viewport, so begin_host_iteration must ignore a non-root update if a child is ever added. It must never be used to infer that a UI pass will follow.
  • Test helpers must preserve that order: raw_input_hook/begin_host_iteration once, then run_ui with tick + ui inside the closure; logic-only runs run_logic with tick only. Do not call tick outside the host-ordered closure in realistic tests.

Both tick and ui keep the existing vectorcraft_engine::guard::catch_panic entry guard: a bug costs one frame, rolls the document back and shows the existing status error; it must not close the app with unsaved work.

Counters (keep them distinct):

  • host_iteration: increments once in begin_host_iteration, for every full or logic-only host update, including repeated hidden iterations and forced hidden paint. It is not a frame or pass count.
  • accepted_ui_frames: derived from Context::cumulative_frame_nr() for the root viewport, which advances once when a run_ui completes and never in run_logic. Compare/store the previous value at tick; count only real completed UI frames. Do not use cumulative_pass_nr() for this.
  • ui_pass_nr: Context::cumulative_pass_nr() for diagnostics only; a discarded pass increments it, so it is not an accepted-frame counter.
  • Replace app.frame uses that mean "outer iteration": native_menu::state_hash uses host_iteration, and artboard key-repeat deadlines use monotonic now_secs rather than a frame delta. If a compatibility frame field remains, define it as host_iteration and document that it also advances on logic-only iterations.

tick rules:

  • Runs when host_iteration != tick_iteration, which is exactly once per host iteration: once for a multi-pass run_ui (the hook ran once before all passes), and once for each logic-only run_logic (the hook ran before the visibility decision). Do not gate it on ctx.cumulative_frame_nr() or on current_pass_index(): after a completed multi-pass frame, current_pass_index() is zero, and a hidden logic-only call does not restore a nonzero pass index.
  • Runs background polls (picks, background, opening, plugin_runs, placing, screen_color, recovery, link watch, font check, control request drain, screenshot completion).
  • Uses monotonic host time (now_secs, see below), never ctx.input(|i| i.time).
  • Reads only viewport state (close_requested, focused, visible) from ctx.input; never raw events, dropped files or text input. Stale events from a previous UI pass must never be consumed here.
  • If tick opens a dialog, a control request injects synthetic input or otherwise changes UI, or a screenshot request is queued but not yet issued (including settling frames) while the viewport is not visible, send ViewportCommand::RequestPaintWhileHidden; a plain repaint runs only logic for a hidden window, not the UI that applies synthetic input, shows the dialog or issues the capture. An already-issued Screenshot command asks for paint itself; every other queued ui.* request needs the explicit command.
  • Keeps ctx.request_repaint_after scheduling for background jobs, autosave, recovery heartbeat and pending screenshots. A logic-only iteration must not stop these. VectorCraft has no audio/playback; the background work that must survive logic-only is file open, background save/export, plug-in runs, Place reads, link checks, font checks, Data Recovery and control/screenshot completion.

ui rules:

  • On the first UI pass of a host iteration (input_iteration != host_iteration), call handle_input_once(ctx) before drawing, inside the same file_access::confine guard as ui_frame when synthetic_frame is set (control-injected input must not escape the automation roots), then set input_iteration = host_iteration:
    • write_formats_before_text_input;
    • native_menu::run;
    • shortcuts::handle, still gated by fonts_ready as today (do not run shortcuts before the UI fonts are bound);
    • native take_dropped_files;
    • synthetic input is already in raw_input_hook; do not drain it again.
  • A later pass of the same host iteration (a request_discard rerun) draws again but does not re-handle input or re-run commands. This is the only place stale/current input is consumed; logic-only has no ui, so no input is replayed. A forced hidden UI paint is still a UI phase and must consume the input it was forced to present.
  • Draws the existing panel order. Multi-pass drawing is allowed; side effects in the drawing code must be event-gated or deferred, not merely assumed idempotent.
  • Measure perf.frame_ms on the first pass but finalize frame statistics only when cumulative_frame_nr() shows the frame was accepted; do not count a discarded pass as another frame.

Scrub undo scopes need an accepted-frame boundary: begin on the first pass that sees a drag, record the release (and cancel flag) on that accepted pass, and commit the scope once in tick at the next host iteration boundary in the document where it began. Do not commit from a pass egui may discard and rerun. Test a scrub release under a forced second pass; the result must be exactly one undo step and no empty second scope.

Multi-pass regression: add a test that forces ctx.request_discard("test") around a frame containing a click on a toolbar/panel command and a new Grid, then asserts exactly one command/undo step and one tick for that host iteration. If a second pass does fire a duplicate command, introduce a narrowly scoped deferred-action queue for the affected UI action; do not add a global compatibility layer and do not set max_passes = 1 (that would accept a mislaid-out Grid).

Logic-only regression: run a full frame with a pending shortcut/click (hook once, then run_ui with tick/ui), then call run_logic(&raw, |ctx| app.tick(ctx)) several times with a fresh begin_host_iteration for each. Assert no command/undo/paste is repeated, background save/recovery/opening continues, tick advances once per call rather than being blocked by a stale pass index, and timers use monotonic time. Also assert no ctx.input event/time read occurs in tick (source/static check or a test clock).

Version-neutral test driver: the 0.36.2 baseline has no tick API. Its driver must use the existing app.logic(ctx) + app.ui(ui) inside run_ui and app.logic(ctx) inside run_logic, preserving the same hook order (call the 0.36.2 host raw_input_hook where the trait provides it; otherwise call its iteration-boundary helper before the pass). The candidate driver uses tick + ui inside run_ui and tick inside run_logic. Record the exact lifecycle and pass count for both in the performance evidence; do not pretend the baseline had a tick surface.

Monotonic clock: add now_secs() beside now_ms using a process-start Instant (native) / web_time::Instant (web). Use it for system_paste_at, font_install_check_at, tick_link_updates, recovery::frame, screenshot deadlines and background scheduling. Keep egui's i.time for UI animation/gesture timing only. recovery::tick/ recovery::frame already accept an explicit now; tests keep using that.
